# 契约 · 删无号壳（memory 侧出口）

状态：**定稿**（2026-10-15 · qwen1）。实现在 `refactor/modules/memory/index.js` 的 `removeNameOnlyMember`，
HTTP 侧由 luna2 接（旧树路由 `DELETE /api/memory-people/name-only?name=…`，`src/app.js:3316-3330`；
`name` 走 query 参数是为了绕开中文/emoji 塞进路径的编码问题，接口层沿用）。

## 一、旧树为什么要有这条路由，新树同一种形状只剩哪一个

旧树一个人一份 `people/<uid>.json`；名字有、QQ 号空的壳记文件名是 `people/_n_<名字>.json`，
数字路由 `/(\d+)` 匹配不上它 ⇒ 只能按名字另开一条（`src/memory.js:2091`）。

新树按 `subjectId` 记观察，**不存在"没有 id 的人"**（《契约-改人物印象.md》§2 起就要求非空），
所以"只有名字、没有号"这件事在新树只剩一种形状：
**`subjects.json` 里有这个显示名，但账本里这个 `subjectId` 连一行观察都没有（生效的和历史的都算）**。
有历史行的人**不归本出口** —— 那是《契约-删成员.md》的活（撤生效观察、留版本链）。

旧树那条 `purgeBadPeople` 式的"名字像句子就清掉"的批量判据没有搬：新树名字只有一个写者
（`store.setSubjectName`，人工改印象时才写），不会出现自动产生的垃圾名；而按名字形状批量删除
一旦判错就是不可恢复的，本出口只做**精确匹配一个名字**。

## 二、签名

```js
export async function removeNameOnlyMember(input): Promise<Result>

input = {
  name,      // 必填 string，trim 后非空 —— 与 subjects.json 里的 name 精确比对（不比大小写之外的东西）
  dataDir,   // 必填
}
```

## 三、返回形状

```js
成功  { ok: true, deleted: true, removedKeys: <条数>, keys: [<subjectId>…], dataDir }

失败  { ok: false, deleted: false, reason: 'not-found' | 'unreadable' | 'unlink-failed',
        dataDir, matchedNameKeys?: <个数>, partial?: { removed, of, note } }
```

`ok/deleted/reason` 键名与 `removeMember` 同构（旧树两个函数同形，接口层共用 `removalSucceeded` +
`memberRemovalFailure(res, reason, /* nameOnly */ true)` 那套判据与文案）。
同名可能有多个键（不同 subjectId 用了同一个显示名）⇒ **全部删掉**，与旧树的 for 循环同义。

## 四、错误码（接口层映射，归 luna2）

| reason | 含义 | 旧树状态码与文案（target=无号壳） |
|---|---|---|
| `not-found` | 没给 `name`；或没有匹配的孤键 | 404「未找到无号壳，未删除」 |
| `unreadable` | `subjects.json` 在盘上但读不出来 / 形状不对 ⇒ **一个键都没删** | 500「记录读不出来，已保留」 |
| `unlink-failed` | 写回失败 ⇒ 已删的键数在 `partial.removed` 里如实给 | 500「删除无号壳失败（精确删除失败）」 |

两条与旧树逐字对齐的细节：
- **空 name 报 `not-found` 不报 `bad-uid`**（旧树注释的理由：这条路由根本没有 uid，报 bad-uid 会让日志误导人）。
- **`unreadable` 绝不能混进 `not-found`**：前者是"记录还在、一条没删"，报 404 等于让用户以为"早就删过了"
  （旧树 N8-b2 专门为此写了 `#unreadablePersonFiles`；新树这份区分落在 `store.readSubjects`）。

★ 新树这条 reason 表**三条全可达**（比 `removeMember` 多一条真的 `unreadable`）：
因为 `subjects.json` 是整份 JSON，解析失败是"这份文件读不出"的确定信号，不像观察账本只给坏行总数。

## 五、本出口明确不做

- 不碰观察账本、不碰证据、不写抑制（要删的就是名字本身）。
- 不模糊匹配、不改名、不合并（合并是《契约-一键清理.md》里那条还没做的件）。
- 读不动就不写：与 `setSubjectName` 同一条门 —— 一次删除不该把整张只是暂时读不懂的表换成"只剩这一条"。
