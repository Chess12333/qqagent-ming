# 契约 · 一键清理（memory 侧出口）

状态：**定稿**（2026-10-15 · qwen1）。实现在 `refactor/modules/memory/index.js` 的 `cleanupAll`，
HTTP 侧由 luna2 接（旧树路由 `POST /api/memory-people/cleanup` → `memory.cleanupAll()`，
`src/app.js:3156-3164`；旧树成功是 `json(res, 200, { ok: true, ...r })`，异常是 500 `{ok:false,error}`）。

## 一、★ 这个出口在新树**不删任何东西**，只如实报状态

旧树那十步里有七步是被"一人一份 `people/<uid>.json`"这份结构逼出来的补丁：同一个人散成多个文件、
只有名字没有号的壳、句子状的垃圾名、近重复印象、失效的表层槽位。新树按 `subjectId` 走追加式账本
（同一个 claimKey 写入时只留一条生效，`store.js:352`；显示名只有一个写者 `setSubjectName`），
**这些缺陷结构上不会出现** ⇒ 本出口报的计数是**真 0**，既不是"清理过了"，也不是"漏做了"。

把 0 写成"清理完成"会让人以为库被扫过一遍；把不可达的说成漏实现会让人以为还要补。
两头都得说清，所以返回里 `notApplicable` / `notImplemented` 是**必读字段**，不是脚注。

## 二、签名

```js
export async function cleanupAll(input): Promise<Result>

input = {
  dataDir,   // 必填
}
```

没有任何删除参数（旧树也没有）：本出口不接受"清哪些人 / 清到什么程度"，全库范围内做判断的件还没实现。

## 三、返回形状

```js
成功  { ok: true,
        merged, mergedQq, purged, deduped, semanticMerged, typesRefined,
        droppedDuplicates, mergeFailures, surfacePruned, surfaceFiles,     // ← 旧树十个字段，一个不少
        scanned: { activeObservations, ledgerRows, namedSubjects, badLedgerLines, subjectsUnreadable? },
        notApplicable: [{ step, why }…],   // 结构上不可能发生，计数为 0
        notImplemented: [{ step, why }…],  // 新树真缺的，等派单
        dataDir, note }
```

- **十个旧字段的含义逐字不变**（照旧树 `src/memory.js:1578` 那条 N7 先例："加字段、不改旧字段含义"）。
  旧路由把结果原样广播 `emit('memory-update', {…r})`、UI 显示"合并 N"，字段名一旦改就是说错话。
- 本轮**全是 0 / 空数组**。这些 0 的含义由 `notApplicable`（四步）与 `notImplemented`（三步）分别承担。
- `scanned` 是新增的**只读计量**：让"为什么是 0"可核对（生效观察数 / 账本总行数 / 有名成员数 / 坏行数）。
  `namedSubjects` 在 `subjects.json` 读不出时给 `null`（不是 0 —— 0 会被读成"一个名字都没有"），
  同时把原因放进 `scanned.subjectsUnreadable`。
- ★ 本出口**不写 `audit.jsonl`**，与另三个出口同一条理由：`logMemoryChange` 的目录是全局解析的，
  per-call 注入 `dataDir` 会写到别的目录去（`suppressions.js` 修过的那个坑）。

## 四、错误码（接口层映射，归 luna2）

memory 侧没有分级失败：本出口没有"参数不合法 / 找不到"这类可达失败态。可达的异常只有一种
—— 账本文件读不出来 ⇒ `openStore` 抛出去，旧路由那条 `catch → 500 {ok:false,error}` 的语义照旧沿用。

| 情形 | 返回 | 旧树状态码 |
|---|---|---|
| 正常（包括"什么都没得清"） | `{ok:true, …十个 0…}` | 200 |
| 账本读不出来（抛异常） | 由 HTTP 侧 catch | 500 `{ok:false,error}` |

## 五、明确不做

- **不删任何东西**：不撤回观察、不动证据、不改名字、不写抑制。要删单个人走《契约-删成员.md》。
- 不调本地模型：旧树的 `dedupeImpressionsSemantic` / `refineImpressionTypes` 靠 Jev 的两个角色，
  旧路由注释写着"但不调云端"、并且整段包在 `try` 里（Jev 没起就少做这两步）。新树**没有合并写回**那半
  （`semantic.js` 只有召回融合 `mergeWithKeyword`）⇒ 这两步点名留在 `notImplemented`，
  等指挥位派单，绝不自作主张扫全库撤回 —— 那两类判断都要动别人的证据链。
- 不做模糊判据："互相包含就算重复"这种旧树判据要不要搬到新树，是**用户/指挥位**的决定，不是实现者的自由发挥。
- 不碰短期状态的年龄闸：`pruneSurface` 那一步在新树是"读时按年龄决定给不给看"（`working-window.js`），
  账本一个字不删 —— 这是设计，不是漏实现。
