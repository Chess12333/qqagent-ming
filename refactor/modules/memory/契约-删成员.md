# 契约 · 删成员（memory 侧出口）

状态：**定稿**（2026-10-15 · qwen1）。实现落在 `refactor/modules/memory/index.js` 的 `removeMember`，
HTTP 侧由 luna2 接 `refactor/apps/server/**`（旧树路由 `DELETE /api/memory-people/:qq`，`src/app.js:3330-3360`）。
配套：《契约-删无号壳.md》《契约-清表层记忆.md》《契约-一键清理.md》；格式照《契约-改人物印象.md》。

## 一、为什么不是照搬老树

老树删成员 = 删掉 `people/<uid>.json` 那份整记录（`impressions/favor/attitude/note/surface` 一起没），
并且**归档先于删除**（`archiveShellRecord` → `backups/_shells/`，归档失败就不删）。
M6 没有"一人一份文件"：一个人的全部记忆 = 账本里若干条**当前生效的观察**（每条指向自己的证据）。
所以这个出口做的是同一件事的三半，且全部走既有出口，不许直接改数据文件：

- 撤回每一条生效观察 → `store.retract`（标 `retracted`，**留历史、不物理删**，`store.js` 不变量④）
- 写来源抑制 → 与 `forget()` 同一套（`writeForgetSuppressions`，reason `manual-member-removal`）；
  不写这一步，后台整理会拿同一批旧消息把这个人重新记回来
- 清显示名 → `store.removeSubjectName`（`<dataDir>/memory/subjects.json` 那个键）

`retract` 会发 `notifyObservationChange` ⇒ 语义索引随之失效重建，本出口不自建第二套失效逻辑。

## 二、签名

```js
// refactor/modules/memory/index.js
export async function removeMember(input): Promise<Result>

input = {
  subjectId,   // 必填 string，trim 后非空、≤64 —— 人物标识（QQ 号或 senderId）
  dataDir,     // 必填：本模块不自读配置（data-dir.js 复盘），由接口层注入
  operator,    // 选填 string，≤40，缺省 'operator' —— 只进撤回原因，供排障回看是谁删的
}
```

★ **旧树第一参数 `chatKey` 不收**：它在旧树函数体里从没被读过（`src/memory.js:2048-2077` 只用 `userId`），
HTTP 侧那句 `memory.removeMember('', userId)` 的 `''` 是个死参数，不传即可。
★ **旧树的 `^\d{5,15}$` 没搬**：新树的 `subjectId` 不只是 QQ 号（可以是 senderId），照搬会把非数字 id 全判成非法。
QQ 号的格式校验留在路由正则 `(\d+)`（接口侧）。

## 三、返回形状

```js
成功  { ok: true, deleted: true,
        retracted: <条数>,
        suppressions: { written: <来源对数>, ok: <bool>, note?: <'no-suppressible-source' 之类> },
        nameRemoved: <bool>,        // subjects.json 那个键确实删掉了
        nameNote?: <字符串>,        // 名字没删掉的原因（观察仍算删成功）
        dataDir, note: '账本留历史，不做物理删除' }

失败  { ok: false, deleted: false, reason: 'bad-uid' | 'not-found' | 'unlink-failed',
        dataDir, partial?: { retracted, total, ids[] } }
```

**`ok` / `deleted` / `reason` 三个键名与旧树逐字一致**：接口层的判据是
`removalSucceeded`（`src/app.js:1231`）= `ok===true && (deleted===true || removed===true) && !reason && !error`。
成功时**必须**带 `deleted:true`：只给 `{ok:true}` 会被它判成失败（那正是旧树 S1 要堵的洞）。
其余字段是追加的（旧消费方不读），先例是旧树 `cleanupAll` 的 N7："加字段、不改旧字段含义"。

## 四、错误码（接口层映射，归 luna2）

| memory 侧 reason | 含义 | 旧树状态码与文案 |
|---|---|---|
| `bad-uid` | subjectId 空或超 64 字 | 400「uid 格式不合法，未删除」 |
| `not-found` | 这个人没有任何生效观察 | 404「未找到该成员，未删除」 |
| `unlink-failed` | 撤回请求发出但有没落地的 | 500「删除成员失败（精确删除失败）」 |

旧树失败表里还有 `archive-failed`、`unreadable` 两条，**新树不可达，不是漏实现**：
账本不做物理删除 ⇒ 没有"归档失败"这一步；坏行只有总数（`store.badLines`，`store.js:76-95`），
定位不到"某个人的行读不出" ⇒ 硬造这条判据等于编。**接口层那两条文案留着不用改表**（永远走不到）。

## 五、本出口明确不做

- 不做"按会话删"：旧树 `clear(chatKey)` 早就废了（全局库按人记，`src/memory.js:2159` 注释），这里同样不引入。
- 不物理删任何行、不清 `changes.jsonl`、不动证据账本：历史必须还能用 `audit()` / `history()` 查到。
- 不写 `audit.jsonl`（`logMemoryChange` 的目录是全局解析的，per-call 注入 dataDir 会写错目录 ——
  与 `suppressions.js` 修过的同一个坑）。变更账走账本自己的 `changes.jsonl`。
- 好感 / 态度（favor、attitude）不在记忆域：同《契约-改人物印象.md》§六，界面传来这两个字段属 `notApplied`，
  本出口根本不收。
