# 契约 · 改人物印象（memory 侧出口）

状态：**定稿**（2026-10-14 · qwen1）。实现落在 `refactor/modules/memory/index.js`，HTTP 侧由 luna2 接 `refactor/apps/server/**`。

## 一、为什么不是照搬老树

老树 `PUT /api/memory-people/:qq` 打的是 `src/memory.js` 的成员印象库（`people[userId]` 一份整记录：`impressions/favor/attitude/note/surface`）。M6 没有这份库：**一个人的"印象"就是账本里若干条当前生效的观察**（`type='impression'`，每条指向自己的证据）。所以这个出口做的是一件事的两半，且都必须走既有出口，不许直接写数据文件：

- 新写的说法 → `commit()`（配一条证据行，见第三节）
- 删掉的说法 → `retract`（`forget()` 那条路：留历史 + 写来源抑制，防后台整理从旧消息里把它捞回来）
- 改说法（更正）→ `commit({supersedes})` ⇒ 行上落 `correction:true`，提示词侧三判据读得到（`prompt/index.js:607`）

`commit`/`forget` 都会发 `notifyObservationChange`，整理器据此重建语义索引 ⇒ **更正当场贯穿到读取路径**（唯一指导 §6.3「旧高分候选不能覆盖明确更正」），本出口不自建第二套失效逻辑。

范围与身份按 §4：人物标识就是 `subjectId`（= personId，出口不重新生成 ID）；新写的条目**默认落 `global`**（全局人物印象跨群，`scope.js` 规则①）。群/私聊里原有的条目**只有调用方把 `scope`/`chatKey` 带回来才改写**——把群内细节静默升成全局是泄露，所以不猜。

## 二、签名

```js
// refactor/modules/memory/index.js
export async function editPersonImpressions(input): Promise<Result>
```

```js
input = {
  subjectId,          // 必填 string，trim 后非空、≤64 —— 人物标识（QQ 号或 senderId）
  impressions,        // 必填 Array<string | Entry>；空数组 = 删光这个人当前生效的印象
  name,               // 选填 string，≤60；给了就写/改 `<dataDir>/memory/subjects.json` 的名字
  operator,           // 选填 string，≤40，缺省 'operator' —— 记进证据行的 speakerId 与变更原因
  scope,              // 选填 'global'|'group'|'private'，缺省 'global'：本次新增条目落哪个范围
  chatKey,            // scope≠'global' 时必填（否则无法判会话范围）
  dataDir,            // 必填：本模块不自读配置（见 data-dir.js 复盘），由装配层/接口层注入
  idempotencyPrefix,  // 选填 string：同一次提交重试不写第二份（键 = `<prefix>:<evidenceId>:manual-impression`）
}

Entry = {
  text,               // 必填 string，≤160（超了截断并如实进 warnings）
  scope, chatKey,     // 选填：这条要保留/写入的范围；不给就用 input.scope / input.chatKey
  replacesId,         // 选填 string：这条是在更正哪条旧观察（给 ⇒ 走 supersedes，落 correction:true）
}
```

条数上限 **60**（沿用老树 `MAX_IMPRESSIONS`）：超出拒写全部（`invalid-arguments`），不静默截断 —— 界面提示那句"只保留 60 条安全阀"要真成立，截断会让人以为存下了。判"同一条"的尺与 `store.js` 一致：trim + 压空白 + 小写。

**更正（带 `replacesId`）不许换范围**：被更正那条是什么范围，新说法就落什么范围（`supersedes` 在账本层也要求 subjectId/scope 一致，见 `store.js:384`）。条目自己显式带了不一致的 `scope`/`chatKey` ⇒ `invalid-arguments` 拒 —— 把群内细节"顺手改成 global"本身就是一次扩范围，不属这个出口的权限。

**`idempotencyPrefix` 不给就不写幂等表**：重复提交的防护来自"证据编号按正文定死 + 重复窗口 + 文字比对判成保留"这三层；幂等表是持久化的，它不知道某条后来被撤回过，默认启用会把"删掉之后又改回来"这次写入顶掉。

## 三、新写条目配的那条证据

M6 的第一不变量是**没有证据不许写**（`store.js` 头 §11）。人工订正不是没有来源：**操作者本人就是来源**。所以每条新增写法生成一条证据行：

```js
{ id: `ev-manual-<subjectId>-<归一正文前 24 字>-<正文 sha256 前 12 位>`,
  at: <本次提交时间>,
  chatKey: <该条目的 chatKey，global 时写 'global'>, kind: <scope 推导>,
  sourceType: 'relay',              // 转述：操作者替这个人陈述，不是这个人自述
  senderId: <operator>, senderName: <operator>,
  subjectIds: [subjectId], text: `人工订正：<原文>` }
```

**这里的字段名是「证据行输入」那套，不是账本落盘那套**（luna2 2026-10-14 查出：原先这行写的是
`speakerId`/`speakerName`，代码照抄 ⇒ `store.normalizeEvidence`（`store.js:275-276`，只认
`sender.id`/`senderId`、`sender.name`/`senderName`）读不到，盘上 `speakerId` 恒为空，
删这条人工条目时 `writeForgetSuppressions` 一个来源对都攒不出 ⇒ 抑制没写、后台整理会把删掉的又捞回来）。
落盘后这两个值就叫 `speakerId`/`speakerName`（读侧 `audit()` 的 `sources[]` 用的是落盘名）。

**编号按正文定死、不带时间**：同一句话重复提交时 `ingestEvidence` 按 id 去重、`writeObservation` 的重复窗口也认"没有新证据"⇒ 不会攒出两份"独立支持"（M6 不变量②）。正文可以带空格/冒号/中文，所以尾段用哈希而不是原文。


`relay` 而非 `self_report`（人没说过这话），也非 `tool_confirm`（不是机器人自己的发言）—— 后两类会被当"她自己说的"打人格归属标，人工订正不该进那一族。

**双人格归属：本出口写观察时显式传 `persona2:false`**（= 不落键，两个人格都看得见）。理由：这条是操作者替某个人陈述的稳定事实，不是"哪一个人格经历的事"；不给就会被 `commit` 按写入时刻在位的人格自动打标，第二人格期间改的印象会在切回第一人格后消失。

## 四、返回形状

成功：

```js
{ ok: true, subjectId, dataDir,
  personExisted,      // 改动前这个人有没有任何生效观察（接口层据此区分"改"与"新建"，仍然 200）
  person: {           // 改完之后这个人的当前生效集合，键名与 GET /api/memory-people 的每人条目一致
    userId, name,
    impressions: [{ id, text, scope, chatKey, at, version, correction? }]
  },
  applied: {
    kept:    [{ id, text, scope, chatKey }],                        // 文字没动 ⇒ 一个字节都不重写
    added:   [{ id, text, scope, chatKey, evidenceId, duplicate }], // duplicate:true = 这句话本来就在（正常不该出现，留给并发/重放）
    revised: [{ id, text, supersedesId, version, correction, duplicate }], // 明确更正（带 replacesId）；correction 按"说法变没变"算
    removed: [{ id, text, scope, chatKey, retracted }],             // retracted:false 只会出现在 write-failed 里
    name:    { from, to } | null,
  },
  suppressions: { written: n } | null,   // 删掉的说法有没有同时被抑制（防整理复活）；无删除时 null
  notApplied: [{ field: 'favor' | 'attitude' | 'note', reason: 'not-memory-owned' }],
  warnings: string[],                    // 例：某条超 160 字被截断
}
```

失败（**不抛异常**，一律返回对象；只有磁盘写失败才抛，由接口层转 500）：

```js
{ ok: false, reason: 'invalid-arguments', errors: ['subjectId: …', 'impressions: …'] }
{ ok: false, reason: 'write-failed', errors: […], partial: { added: [...], removed: [...] } }
```

`write-failed` 的 `partial` 必须有：观察是追加写，中途失败时已写进去的不会回滚，如实说哪几条成了，不许回一句"失败"假装什么都没发生。

## 五、错误码（接口层映射，归 luna2）

| memory 返回 | HTTP | 说明 |
|---|---|---|
| `ok:true` | **200** | 含"这个人原本不存在"（`personExisted:false`）—— 老树 `editMemberImpression` 对没这个人也是建一份，**PUT 侧没有 404** |
| `reason:'invalid-arguments'` | **400** | 入参不合格，`errors[]` 原样带出 |
| `reason:'write-failed'` / 抛异常 | **500** | 落盘失败 |

老树分级同样是 **PUT 只有 400**（`src/app.js:3330-3344` 一个 `catch` 全转 400），404/500 是 DELETE（`memberRemovalFailure`）那一族 —— 本契约不把 DELETE 揽进来。

`notApplied` 非空时接口层要在响应里可见，界面据此告诉用户"好感/态度/备注没由这次保存改动"（好感归 §7 情绪域，`emotion.relationOf` 读、`memory_favor` 工具写）。**不许静默吞掉**：老树那次 PUT 把 `favor/attitude/note` 一起写进成员记录，M6 若无脑接了又什么都不写，就是界面说谎。

## 六、本出口明确不做

- 不写 favor / attitude / note / surface（无对应存储；surface 在 M6 是 `type='recent'`，按半衰过期，N67 已裁定不设手动精删入口）
- 不碰 `apps/server/**`、不碰 `apps/ui/**`（HTTP 形状与界面文案归 luna2）
- 不改 `memory.manualEditLockMs` 那类整理黑窗（配置键当前零读点，属另一件事，不在本单内顺手接）
- 不做批量 / 跨人编辑（一次一个人）
