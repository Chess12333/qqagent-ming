# 契约 · 清表层记忆（memory 侧出口）

状态：**定稿**（2026-10-15 · qwen1）。实现在 `refactor/modules/memory/index.js` 的 `clearSurface`，
HTTP 侧由 luna2 接（旧树路由 `DELETE /api/memory-people/:qq/surface`，`src/app.js:3362-3370`）。

## 一、"表层记忆"在新树是什么

旧树一个人的记录里有一格 `surface`（近况：身体 / 情绪 / 在做什么 / 等 / 计划，槽位键 + `surfaceKindOf`
判 kind，`src/memory.js:470`），它会自己半衰，这个入口是给"记错了 / 不想要"用的手动闸门。

M6 没有 `surface` 这一格。同一层的东西是账本里的 **D 层短期状态**：
`type ∈ 'topic' | 'promise' | 'question' | 'recent'`（`working-window.js:40 SHORT_TERM_TYPES`
/ `isShortTermType`，与 `store.js` 头注释的 C/D 分层同一把尺）。
**C 层的稳定认识（impression / trait / preference / fact）一律不碰** —— "清一下近况"
不该把一个人长期的东西一起抹掉，这与旧树只删 `m.surface` 不删 `m.impressions` 同义。

## 二、签名

```js
export async function clearSurface(input): Promise<0 | 1>

input = {
  subjectId,    // 必填 string —— 人物标识
  chatKey,      // 选填 string|null：null（缺省）= 这个人所有会话的短期状态都清；给了就只清那个会话
  dataDir,      // 必填
  operator,     // 选填 string，≤40，缺省 'operator' —— 只进撤回原因
  diagnostics,  // 选填 object：想细看本次删了什么就传一个空对象，函数往里写
                // { matched, retracted, missed, reason? }
}
```

★ **两处与旧树不一样，都是结构造成的，不是自由发挥**：

1. **不收 `kind`**。旧树第三个参数是 surface 的 kind（body|mood|doing|wait|plan），
   新树行上没有这一维（只有 `type` / `scope` / `chatKey`）。收一个只能假装有用的参数比不收更坏。
   ⚠ 接口层那条 `?kind=` 查询串怎么办**归 luna2 裁**：明确回 400「新树没有表层 kind 维度」，
   或干脆忽略并写在界面说明里 —— 都比静默当成别的维度处理强。
2. **本出口是 async**。旧树同步改文件；新树撤回必须走 `store.retract`（带锁 + 写 `changes.jsonl`
   + 发 `notifyObservationChange` 让语义索引随之失效）。

## 三、返回形状

**数字 `1 / 0`，与旧树逐字同形**：旧路由是 `const removed = memory.clearSurface(...)`
→ `json(res, 200, { ok: true, removed })`（`src/app.js:3362`）。
改成对象会让接口层那句话说不通，所以这里宁可把明细放到 `diagnostics` 出参里。

- `1` = 这次确实清掉了东西（≥1 条被撤回）
- `0` = 没有可清的（`diagnostics.reason='no-active-surface'`），或撤回一行都没落地
  （`diagnostics.reason='retract-incomplete'` + `missed` 给条数）

`chatKey` 缺省（null）的语义也与旧树一致：`chatKey == null` ⇒ 不按会话过滤（旧树同一条判断）。

## 四、错误分级

本出口没有失败码（旧树也没有：它连 `writeJson` 的异常都 `catch {} ignore`）。
新树不重复那个"静默忽略"：撤回没落地会通过 `diagnostics.missed / reason` 如实带出来，
调用方（接口层）想报 500 就有依据。

★ 与旧树同的一点：删掉的近况**同样写来源抑制**（reason `manual-surface-clear`）。
旧树不需要这一步（它物理删了槽位），新树账本不删 ⇒ 不写抑制的话，后台整理会拿同一批旧消息
把它再写回来 —— 与《契约-删成员.md》第三节那条完全同理。

## 五、本出口明确不做

- 不碰 C 层稳定认识；不碰证据账本；不物理删行（历史仍可用 `audit()` / `history()` 查）。
- 不改显示名、不动 `subjects.json`。
- 不做"按时间/浓度阈值清"：旧树的衰减由 `pruneSurface` 负责，而新树的衰减是**读时年龄闸**
  （`working-window.js`，账本一个字不删，见《契约-一键清理.md》为什么 `surfacePruned` 恒 0）。
